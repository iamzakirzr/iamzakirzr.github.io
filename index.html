01 — ABOUT

What I actually do

THE DAY JOB

Frameworks other engineers can live in

I'm a Senior QA Engineer at IQVIA, on healthcare and life sciences platforms where "it looked fine when I clicked it" is not an acceptable standard of evidence. Most of my career has gone into building test automation frameworks in Playwright, Selenium, Cypress, AccelQ, Python and C#, wired into Azure DevOps so the regression suite runs itself every day instead of the night before a release.

I also lead a team of five QA engineers and own the STLC across Scrum, Kanban and Waterfall, which mostly means translating between what a test report says and what a release manager needs to hear.

Team of fiveFull STLCTest strategyQuality governance
THE NEWER HALF

Systems that don't behave the same way twice

Enterprise chatbots, RAG pipelines and agentic workflows don't fail like deterministic software does: they fail quietly, fluently, and only sometimes. So I build evaluation frameworks instead of assertions: golden datasets, scored metrics, thresholds a pipeline can fail on.

A drop in faithfulness gets handled the same way I'd handle a red test. That is the whole idea: make the non-deterministic thing fail loudly, early, and in CI.

LLM evaluationRAG pipelinesAgentic workflowsCI gating

FRAMEWORK DESIGN

Page Object Model, underneath everything

Locators and page behaviour live in one place, so a UI change is one edit instead of fifty and the tests above read as intent rather than selectors. Reusable libraries sit under that, shared across suites, which is what makes a new test cost hours rather than days.

The same design carries across Playwright, Selenium and Cypress on the web, and Squish and AccelQ beyond it, in Python and C# alike. Built to be something other engineers can work in rather than around.

PlaywrightSeleniumCypressPythonC#/.NETPyTestNUnitAccelQ
ONE SUITE, EVERY LAYER

UI, API, database and the message bus in one run

A Python and Playwright framework validating UI, API and database together. Contract and schema checks sit under the UI tests, and SQL-level assertions catch data-integrity faults directly instead of letting them surface later as a confusing screen.

Where the system is event-driven that extends to the message layer: asserting what actually lands on a Kafka topic, and how consumers behave once it does. A queue that silently drops a message fails no UI test, which is exactly why it needs its own.

03 — AI QUALITY ENGINEERING

Testing what can be fluent and wrong

A model that is confidently incorrect passes every assertion you would write for ordinary software. These are the four checks that catch it.

LLM & RAG EVALUATION

Golden datasets, then scored runs

Faithfulness, context precision, answer relevance and hallucination rate, scored run over run. DeepEval and RAGAS sit in the loop so a drop in response quality surfaces as a failing check rather than a support ticket three weeks later.

RAGASDeepEvalGolden datasetsContext precision
AGENTIC WORKFLOWS

Judged on what they did, not what they said

Multi-step agents get measured on tool-calling accuracy, reasoning traces, autonomous task execution, and whether context is still intact by step six.

Tool-callingReasoning tracesContext retentionLangSmith
CONVERSATIONAL AI

Flows, intent, and the fallback path

End-to-end quality engineering for enterprise chatbots: conversational flows, intent recognition, and behaviour when the model has nothing useful to say. Deterministic guardrails catch the contract violations a pattern can express; semantic scoring covers the far larger set it can't.

Intent recognitionFallback pathsRegex guardrailsFlow coverage
ROBUSTNESS & SAFETY

Finding where it stops being trustworthy

Prompt-injection probing and bias testing, sweeping temperature, confidence thresholds and context memory to locate the point where a model stops being safe to ship. Better that I find it than a user does.
